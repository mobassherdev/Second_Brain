## Object-Oriented Programming (OOP)

## Question: What is Object-Oriented Programming?

## Answer:
Object-Oriented Programming (OOP) is a programming paradigm that organizes software design around objects rather than functions and logic. An object is a data field that has unique attributes and behavior. OOP focuses on creating reusable and modular code by grouping related data and methods into objects.

I think of OOP as a way to model real-world entities in code. Instead of writing procedural steps, you define objects that know things (state) and do things (behavior). This makes code more intuitive, maintainable, and scalable for complex systems.

OOP is built on four pillars: encapsulation, abstraction, inheritance, and polymorphism. Together, these concepts help developers write code that is modular, reusable, and easier to debug.

## Key Points:
- OOP organizes code around objects, not functions.
- Objects contain both data (attributes) and behavior (methods).
- Four pillars: encapsulation, abstraction, inheritance, polymorphism.
- Promotes code reuse and modularity.
- Models real-world entities in software.

## Interview Tip:
Explain OOP by contrasting it with procedural programming. Give a real-world analogy like modeling a car â€” it has properties (color, speed) and behaviors (accelerate, brake).

---

## Question: Why do we use OOP?

## Answer:
We use OOP because it provides a clear structure for programs, makes code reusable, and allows developers to build complex systems from smaller, manageable pieces. OOP reduces code duplication through inheritance and promotes separation of concerns through encapsulation.

In my experience, OOP becomes essential when projects grow beyond a few hundred lines. It allows multiple developers to work on different parts of the system independently. Each object handles its own state and exposes a clean interface to the outside world.

OOP also makes testing easier. You can test individual classes in isolation using mock objects. This modularity leads to more maintainable, scalable, and robust applications.

## Key Points:
- Provides clear program structure.
- Promotes code reuse via inheritance and composition.
- Makes large codebases manageable.
- Enables modular testing with mock objects.
- Supports separation of concerns.

## Interview Tip:
Give a concrete example: "In a banking system, OOP lets me model Account, Customer, and Transaction as separate objects, each with their own responsibilities."

## Question: What are the four pillars of OOP?

## Answer:
The four pillars of OOP are Encapsulation, Abstraction, Inheritance, and Polymorphism. Encapsulation bundles data and methods into a single unit and restricts direct access to some components. Abstraction hides complex implementation details and exposes only what's necessary.

Inheritance allows a class to acquire the properties and behaviors of another class, promoting code reuse. Polymorphism allows objects of different types to be treated as objects of a common type, enabling the same method to behave differently based on the object's actual class.

Together, these pillars enable developers to write modular, reusable, and maintainable code. They form the foundation of object-oriented design and are essential for building scalable applications.

## Key Points:
- Encapsulation: bundles data and methods, restricts access.
- Abstraction: hides complexity, exposes simple interfaces.
- Inheritance: promotes code reuse through parent-child relationships.
- Polymorphism: same interface, different implementations.
- These pillars work together to create robust systems.

## Interview Tip:
Don't just list the pillars â€” explain how they work together. For example, "Encapsulation makes abstraction possible because you can hide internal details behind a public interface."

## Question: What is a class?

## Answer:
A class is a blueprint or template for creating objects. It defines the properties (attributes) and behaviors (methods) that objects of that type will have. Think of a class as a cookie cutter â€” it defines the shape, and each cookie (object) is an instance of that shape.

In Java, a class might look like this:

```java
public class Car {
    private String color;
    private int speed;
    
    public Car(String color) {
        this.color = color;
        this.speed = 0;
    }
    
    public void accelerate() {
        speed += 10;
    }
    
    public int getSpeed() {
        return speed;
    }
}
```

A class itself doesn't take up memory for its properties â€” only the objects created from it do. Classes are the building blocks of OOP and enable encapsulation, inheritance, and polymorphism.

## Key Points:
- A class is a blueprint for creating objects.
- Defines attributes (data) and methods (behavior).
- Does not occupy memory for properties until instantiated.
- Enables code reuse and structure.
- Supports encapsulation, inheritance, and polymorphism.

## Interview Tip:
Use the cookie cutter analogy. Mention that a class is like a data type, and objects are the actual instances.

## Question: What is an object?

## Answer:
An object is an instance of a class. It's a concrete entity in memory that has its own state (values for the class's attributes) and can perform actions (methods defined in the class). If a class is a blueprint, an object is the actual building constructed from that blueprint.

When you create an object, memory is allocated for its properties. Each object has its own copy of instance variables. Multiple objects can be created from the same class, each with different state.

```java
Car myCar = new Car("red");    // object 1
Car yourCar = new Car("blue"); // object 2
```

Objects interact with each other through method calls. This interaction is what makes OOP powerful â€” you model real-world systems by defining how objects communicate and collaborate.

## Key Points:
- An object is an instance of a class.
- Has its own state (instance variables) and behavior (methods).
- Memory is allocated when an object is created.
- Multiple objects can be created from one class.
- Objects interact through method calls.

## Interview Tip:
Emphasize that objects are runtime entities while classes are compile-time constructs. This distinction is important for understanding memory allocation.

## Question: What is the difference between a class and an object?

## Answer:
A class is a blueprint or template; an object is an instance of that class. A class defines what properties and methods an object will have, but it doesn't occupy memory for those properties. An object is a concrete entity in memory that holds actual values.

Think of it this way: "Car" is a class (a concept), while "my red Honda" is an object (a specific car). You can create hundreds of car objects from the same class, each with different colors, speeds, and models.

| Class | Object |
|-------|--------|
| Blueprint | Instance |
| Logical entity | Physical entity |
| No memory for properties | Memory allocated |
| Defined once | Created many times |

In code, you declare a class once and instantiate it many times to create objects.

## Key Points:
- Class = blueprint, Object = instance.
- Class has no memory for properties; objects do.
- One class can create many objects.
- Classes are defined at compile time; objects exist at runtime.
- Objects have unique state even though they share the same class definition.

## Interview Tip:
Use the cookie cutter analogy again. Also mention that classes are reference types in Java and objects are instances stored on the heap.

## Question: What is encapsulation?

## Answer:
Encapsulation is the bundling of data (variables) and methods that operate on that data into a single unit (class), while restricting direct access to some of the object's components. It's achieved through access modifiers like private, protected, and public.

I use encapsulation to protect the internal state of an object. By making fields private and providing public getter/setter methods, I control how data is accessed and modified. This prevents external code from putting the object into an invalid state.

```java
public class BankAccount {
    private double balance;
    
    public double getBalance() {
        return balance;
    }
    
    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }
}
```

Encapsulation is fundamental to OOP because it enables data hiding, makes code easier to maintain, and allows the internal implementation to change without affecting external code.

## Key Points:
- Bundles data and methods into a single unit.
- Restricts direct access to internal state.
- Uses access modifiers (private, public, protected).
- Enables data hiding and validation.
- Protects object integrity.

## Interview Tip:
Give an example where direct access would be dangerous â€” like allowing negative bank balances. Show how encapsulation prevents that.

## Question: What is abstraction?

## Answer:
Abstraction is the concept of hiding complex implementation details and exposing only the essential features of an object. It focuses on what an object does rather than how it does it. Abstraction is achieved through abstract classes and interfaces.

I think of abstraction as creating a simplified view of complex systems. When you drive a car, you interact with the steering wheel, pedals, and gear shift â€” you don't need to understand the internal combustion engine. That's abstraction in action.

```java
public interface PaymentProcessor {
    void processPayment(double amount);
}

public class CreditCardProcessor implements PaymentProcessor {
    public void processPayment(double amount) {
        // Complex credit card processing logic hidden here
    }
}
```

Abstraction reduces complexity, improves code readability, and allows developers to focus on high-level design rather than getting lost in implementation details.

## Key Points:
- Hides complex implementation details.
- Exposes only essential features.
- Achieved through interfaces and abstract classes.
- Focuses on what, not how.
- Reduces cognitive load for developers.

## Interview Tip:
Use the car analogy. Also mention that abstraction and encapsulation work together â€” encapsulation hides data, abstraction hides complexity.

## Question: What is inheritance?

## Answer:
Inheritance is a mechanism where a new class (child/subclass) acquires the properties and behaviors of an existing class (parent/superclass). It promotes code reuse and establishes a natural hierarchy between classes. The child class can override or extend the parent's behavior.

I use inheritance when there's a clear "is-a" relationship. For example, a Dog is an Animal, so Dog can inherit from Animal. This avoids duplicating common properties and methods.

```java
public class Animal {
    public void eat() {
        System.out.println("Eating...");
    }
}

public class Dog extends Animal {
    public void bark() {
        System.out.println("Barking...");
    }
}
```

Inheritance is powerful but should be used carefully. Overusing it can lead to tight coupling and fragile base class problems. Composition is often preferred as an alternative.

## Key Points:
- Child class inherits from parent class.
- Promotes code reuse through "is-a" relationships.
- Child can override or extend parent behavior.
- Supports polymorphism.
- Can lead to tight coupling if overused.

## Interview Tip:
Explain the "is-a" relationship clearly. Warn about the diamond problem in multiple inheritance and how Java handles it with interfaces.

## Question: What is polymorphism?

## Answer:
Polymorphism means "many forms" â€” it allows objects of different types to be treated as objects of a common type. The same method call can behave differently depending on the actual type of the object. This is one of the most powerful features of OOP.

There are two types: compile-time polymorphism (method overloading) and runtime polymorphism (method overriding). Compile-time polymorphism is resolved at compile time based on method signatures. Runtime polymorphism is resolved at runtime based on the actual object type.

```java
public class Animal {
    public void sound() {
        System.out.println("Some sound");
    }
}

public class Dog extends Animal {
    public void sound() {
        System.out.println("Bark");
    }
}

public class Cat extends Animal {
    public void sound() {
        System.out.println("Meow");
    }
}

// Runtime polymorphism
Animal myAnimal = new Dog();
myAnimal.sound(); // Output: Bark
```

Polymorphism makes code more flexible and extensible. You can add new types without changing existing code that uses the base type.

## Key Points:
- Same interface, different implementations.
- Compile-time: method overloading.
- Runtime: method overriding.
- Makes code flexible and extensible.
- Enables programming to an interface, not an implementation.

## Interview Tip:
Give a clear example showing method overriding. Explain that the JVM determines which method to call at runtime â€” this is dynamic dispatch.

## Classes & Objects

## Question: How do you design a class?

## Answer:
Designing a class involves identifying the responsibilities, attributes, and behaviors that the class should have. I start by asking: "What does this entity need to know?" (attributes) and "What does it need to do?" (methods). Then I apply principles like single responsibility and encapsulation.

First, I identify the class name based on the real-world or conceptual entity it represents. Then I define the attributes as private fields and create public methods to interact with them. I also think about relationships â€” does this class need to interact with other classes?

```java
public class User {
    private String name;
    private String email;
    private List<Order> orders;
    
    public User(String name, String email) {
        this.name = name;
        this.email = email;
        this.orders = new ArrayList<>();
    }
    
    public void placeOrder(Order order) {
        orders.add(order);
    }
    
    public List<Order> getOrders() {
        return Collections.unmodifiableList(orders);
    }
}
```

Good class design follows SOLID principles, uses meaningful names, and keeps responsibilities focused.

## Key Points:
- Identify responsibilities, attributes, and behaviors.
- Apply single responsibility principle.
- Use meaningful class and method names.
- Keep fields private, expose through methods.
- Think about relationships with other classes.

## Interview Tip:
Walk through your thought process step by step. Interviewers want to see how you break down requirements into class design.

## Question: What makes a good class design?

## Answer:
A good class design follows the Single Responsibility Principle â€” it has one reason to change. It has a clear, focused purpose, meaningful names, and a minimal public API. The internal state is hidden behind encapsulation, and the class is easy to test.

I also look for loose coupling â€” the class should depend on abstractions rather than concrete implementations. It should be easy to use correctly and hard to use incorrectly. This means validating inputs, providing clear documentation, and designing intuitive interfaces.

Key indicators of good class design: the class is small (under 200 lines), has a focused set of methods, uses composition over inheritance, and can be independently tested with mock dependencies.

## Key Points:
- Follows Single Responsibility Principle.
- Has a clear, focused purpose.
- Minimal public API â€” exposes only what's necessary.
- Easy to test and use.
- Loose coupling with dependencies.

## Interview Tip:
Mention that good class design evolves over time. Refactoring is a normal part of the process as you learn more about the problem domain.

## Question: What is a constructor?

## Answer:
A constructor is a special method that is called when an object is created. It initializes the object's state and allocates resources. In Java, the constructor has the same name as the class and no return type. In TypeScript, you use the `constructor` keyword.

Constructors allow you to set initial values for object properties. They can be overloaded to provide different ways of creating objects. A class can have multiple constructors with different parameter lists.

```java
public class User {
    private String name;
    private String email;
    
    // Default constructor
    public User() {
        this.name = "Unknown";
        this.email = "";
    }
    
    // Parameterized constructor
    public User(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

Constructors are essential for ensuring objects start in a valid state. Without them, you'd have to manually initialize every object after creation.

## Key Points:
- Special method called during object creation.
- Initializes object state.
- Same name as class, no return type.
- Can be overloaded.
- Ensures objects start in a valid state.

## Interview Tip:
Explain the difference between default and parameterized constructors. Mention that if you define any constructor, Java won't provide a default one.

---

## Question: What is the purpose of a constructor?

## Answer:
The purpose of a constructor is to initialize an object's state when it's created. It ensures that every object starts with valid initial values and that all required dependencies are provided. Without a constructor, objects might be in an incomplete or invalid state.

I use constructors to enforce required dependencies. If a User class needs a name and email, I make those constructor parameters mandatory. This way, it's impossible to create a User without providing the necessary information.

Constructors also help with immutability. By setting values in the constructor and not providing setters, you can create immutable objects that are thread-safe and predictable.

## Key Points:
- Initializes object state at creation time.
- Enforces required dependencies.
- Ensures objects start in a valid state.
- Enables immutability when combined with final fields.
- Prevents incomplete or inconsistent objects.

## Interview Tip:
Explain that constructors are about invariant enforcement â€” ensuring certain conditions are always true when an object exists.

## Question: What are instance variables?

## Answer:
Instance variables are variables declared inside a class but outside any method. Each object (instance) of the class has its own copy of these variables. Their values are unique to each object and can change over the object's lifetime.

Instance variables define the state of an object. When you create a new object, memory is allocated for its instance variables. They are accessible throughout the class using `this` keyword.

```java
public class Car {
    private String color;  // instance variable
    private int speed;     // instance variable
    
    public void accelerate() {
        speed += 10;  // accessing instance variable
    }
}
```

Instance variables are different from local variables (declared inside methods) and class variables (static). Each object maintains its own state independently.

## Key Points:
- Declared inside a class, outside methods.
- Each object has its own copy.
- Defines the object's state.
- Accessible throughout the class.
- Persist as long as the object exists.

## Interview Tip:
Contrast instance variables with local variables and static variables. Explain that instance variables are stored on the heap as part of the object.

## Question: What are class/static variables?

## Answer:
Class variables (static variables) are variables declared with the `static` keyword inside a class. Unlike instance variables, there is only one copy shared across all instances of the class. They belong to the class itself, not to any particular object.

Static variables are useful for maintaining shared state or constants. They are initialized when the class is loaded and exist throughout the program's lifetime.

```java
public class User {
    private static int totalUsers = 0;
    private String name;
    
    public User(String name) {
        this.name = name;
        totalUsers++;
    }
    
    public static int getTotalUsers() {
        return totalUsers;
    }
}
```

In this example, `totalUsers` is shared among all User objects. Every time a new User is created, the count increments. This is how you track global state within a class.

## Key Points:
- Declared with `static` keyword.
- One copy shared across all instances.
- Belongs to the class, not objects.
- Initialized when class is loaded.
- Useful for constants and shared state.

## Interview Tip:
Give a clear example like a counter or a constant. Explain that static methods can only access static variables directly.

## Question: What are instance methods?

## Answer:
Instance methods are methods defined inside a class that operate on a specific instance of the class. They can access and modify instance variables. When you call an instance method, you need an object of that class to call it on.

Instance methods define the behavior of objects. They can use `this` to reference the current object and access its instance variables. They can also call other instance methods.

```java
public class Calculator {
    private double result;
    
    public void add(double value) {  // instance method
        result += value;
    }
    
    public double getResult() {  // instance method
        return result;
    }
}
```

Instance methods are the primary way objects interact with their state. They can be overridden in subclasses to provide different implementations (polymorphism).

## Key Points:
- Defined inside a class, require an object to call.
- Can access instance variables.
- Can call other instance methods.
- Define object behavior.
- Can be overridden for polymorphism.

## Interview Tip:
Contrast with static methods â€” instance methods need an object, static methods don't. Explain that instance methods are how objects "do things."

## Question: What are static methods?

## Answer:
Static methods belong to the class itself rather than any particular instance. They can be called without creating an object of the class. Static methods cannot access instance variables or instance methods directly â€” they can only work with static members.

I use static methods for utility functions, factory methods, and operations that don't depend on object state. They are often used for helper functions that perform calculations or validations.

```java
public class MathUtils {
    public static int add(int a, int b) {
        return a + b;
    }
    
    public static boolean isEven(int number) {
        return number % 2 == 0;
    }
}

// Usage
int result = MathUtils.add(5, 3);
```

Static methods are useful but should be used sparingly. Overusing static methods can make code hard to test because they can't be easily mocked or overridden.

## Key Points:
- Belong to the class, not instances.
- Can be called without creating an object.
- Cannot access instance variables directly.
- Useful for utility and factory methods.
- Can be overridden but not polymorphically.

## Interview Tip:
Explain that static methods are resolved at compile time (not runtime), so they don't participate in polymorphism. This is an important distinction.

## Question: What is object composition?

## Answer:
Object composition is a design technique where a class contains references to other objects as its fields, rather than inheriting from them. It establishes a "has-a" relationship between objects. Composition is often preferred over inheritance because it's more flexible and avoids tight coupling.

I use composition when an object needs functionality from another class but there isn't a clear "is-a" relationship. Instead of inheriting, the object contains an instance of the other class and delegates work to it.

```java
public class Engine {
    public void start() {
        System.out.println("Engine started");
    }
}

public class Car {
    private Engine engine;  // composition
    
    public Car() {
        this.engine = new Engine();
    }
    
    public void start() {
        engine.start();
    }
}
```

Composition makes code more modular and easier to modify. You can change the contained object's implementation without affecting the container class.

## Key Points:
- "Has-a" relationship between objects.
- Class contains references to other objects.
- More flexible than inheritance.
- Promotes loose coupling.
- Enables runtime behavior changes.

## Interview Tip:
Explain the "has-a" vs "is-a" distinction. Give an example where composition is clearly better than inheritance.

---

## Question: What is the difference between composition and inheritance?

## Answer:
Inheritance establishes an "is-a" relationship (Dog is an Animal), while composition establishes a "has-a" relationship (Car has an Engine). Inheritance couples the child tightly to the parent, while composition allows more flexibility.

With inheritance, the child class gets all of the parent's methods and fields. With composition, the containing class explicitly chooses which methods to expose by delegating calls to the contained object.

| Composition | Inheritance |
|-------------|-------------|
| Has-a relationship | Is-a relationship |
| Loose coupling | Tight coupling |
| Flexible at runtime | Fixed at compile time |
| Easy to change behavior | Hard to change parent |
| Preferred in most cases | Use when clear hierarchy |

In most cases, I prefer composition over inheritance. Inheritance should only be used when there's a genuine hierarchical relationship and you want to reuse the parent's implementation.

## Key Points:
- Composition: "has-a", Inheritance: "is-a".
- Composition is more flexible and loosely coupled.
- Inheritance is rigid â€” child is tied to parent's implementation.
- Composition allows runtime behavior changes.
- Prefer composition unless there's a clear hierarchy.

## Interview Tip:
Give a clear example: "A Car has an Engine (composition), but a Car is not an Engine (not inheritance)." This distinction is key.

## Encapsulation & Abstraction

## Question: Why is encapsulation important?

## Answer:
Encapsulation is important because it protects the internal state of objects from being corrupted by external code. By hiding the internal representation and exposing only a controlled interface, you prevent invalid states and unauthorized access.

Without encapsulation, any code could directly modify an object's fields, potentially putting it in an inconsistent state. For example, without encapsulation, someone could set a bank account balance to a negative number without any validation.

Encapsulation also makes code easier to maintain. When the internal implementation changes, only the class itself needs to be updated â€” external code that uses the public interface remains unchanged. This separation of concerns is fundamental to building robust, maintainable systems.

## Key Points:
- Protects object state from external corruption.
- Prevents invalid states through controlled access.
- Enables internal changes without affecting external code.
- Supports validation and business rules.
- Fundamental to maintainable OOP code.

## Interview Tip:
Give a concrete example like a bank account where direct field access would allow negative balances. Show how encapsulation prevents this.

---

## Question: How do you implement encapsulation?

## Answer:
Encapsulation is implemented by making class fields private and providing public getter and setter methods to access and modify them. The getter and setter methods can include validation logic to ensure the object remains in a valid state.

In Java, you use the `private` access modifier on fields and `public` on methods. In TypeScript, you use the `private` or `#` keyword.

```java
public class User {
    private String name;
    private int age;
    
    public String getName() {
        return name;
    }
    
    public void setName(String name) {
        if (name != null && !name.isEmpty()) {
            this.name = name;
        }
    }
    
    public int getAge() {
        return age;
    }
    
    public void setAge(int age) {
        if (age >= 0 && age <= 150) {
            this.age = age;
        }
    }
}
```

The key is to validate inputs in setters and prevent external code from directly manipulating internal state. You can also make fields final for immutability.

## Key Points:
- Make fields private.
- Provide public getter/setter methods.
- Add validation in setters.
- Use final for immutability.
- Control access to internal state.

## Interview Tip:
Show code with validation in setters. Explain that you can also use read-only objects by providing only getters.

## Question: What are access modifiers?

## Answer:
Access modifiers are keywords that control the visibility and accessibility of classes, methods, and variables. They are a key mechanism for implementing encapsulation. The four main access modifiers in Java are public, protected, default (package-private), and private.

| Modifier | Class | Package | Subclass | World |
|----------|-------|---------|----------|-------|
| public | Yes | Yes | Yes | Yes |
| protected | Yes | Yes | Yes | No |
| default | Yes | Yes | No | No |
| private | Yes | No | No | No |

I choose access modifiers based on the narrowest possible visibility. If a method is only used within the class, I make it private. If it needs to be accessible to subclasses, I use protected.

## Key Points:
- Control visibility of classes, methods, variables.
- Four levels: public, protected, default, private.
- public = accessible everywhere.
- private = accessible only within the class.
- Choose the narrowest visibility possible.

## Question: What is public access?

## Answer:
Public access means a class, method, or variable is accessible from anywhere â€” from within the class, from other classes in the same package, from subclasses, and from completely unrelated classes. It's the least restrictive access modifier.

I use public access for the class's interface â€” the methods and properties that other code needs to interact with. A public API should be well-designed because changing it can affect many parts of the system.

```java
public class UserService {
    public User getUserById(String id) {
        // implementation
    }
    
    public void createUser(User user) {
        // implementation
    }
}
```

Public access should be used carefully. Everything public becomes part of the API contract, and changing it later can break dependent code. Prefer making things private and only exposing what's necessary.

## Key Points:
- Accessible from anywhere.
- Least restrictive modifier.
- Used for class interfaces and public APIs.
- Changes can affect the entire system.
- Use sparingly â€” prefer private when possible.

## Question: What is private access?

## Answer:
Private access means a class member (variable or method) is only accessible within the same class. It cannot be seen or used by any other class, including subclasses. This is the most restrictive access modifier and is essential for encapsulation.

I make fields private to hide the internal state of objects. I also make helper methods private if they should not be part of the public API.

```java
public class BankAccount {
    private double balance;
    
    private void logTransaction(String type, double amount) {
        // internal logging
    }
    
    public void deposit(double amount) {
        balance += amount;
        logTransaction("DEPOSIT", amount);
    }
}
```

Private members are the implementation details of a class. They can be changed freely without affecting external code. This is the foundation of encapsulation.

## Key Points:
- Only accessible within the same class.
- Most restrictive modifier.
- Hides implementation details.
- Foundation of encapsulation.
- Can be changed without affecting external code.

## Interview Tip:

## Question: What is protected access?

## Answer:
Protected access means a member is accessible within the same package and by subclasses (even in different packages). It's more restrictive than public but less restrictive than default (package-private).

I use protected access when I want subclasses to be able to access or override a member, but I don't want it to be accessible to unrelated classes in the same package.

```java
public class Animal {
    protected void eat() {
        System.out.println("Eating...");
    }
}

public class Dog extends Animal {
    public void bark() {
        eat();  // can access protected method
        System.out.println("Barking...");
    }
}
```

Protected members form the "contract" between a parent class and its subclasses. They allow subclasses to customize behavior while maintaining the parent's structure.

## Key Points:
- Accessible in same package and subclasses.
- More restrictive than public.
- Used for subclass customization.
- Part of the parent-child contract.
- Not accessible to unrelated classes.

## Interview Tip:
Explain the difference between protected and default access. Protected extends access to subclasses outside the package, default does not.

## Question: What is data hiding?

## Answer:
Data hiding is a principle of encapsulation where the internal data of an object is hidden from the outside world. Only the object's methods can access and modify its data. This prevents unauthorized access and ensures data integrity.

I implement data hiding by making fields private and providing controlled access through getter and setter methods. The methods can validate inputs and enforce business rules.

```java
public class User {

    public boolean verifyPassword(String password) {
        return this.password.equals(hashPassword(password));
    }
}
```

Data hiding is crucial for security, maintainability, and preventing bugs. Without it, external code could corrupt the object's state or access sensitive information.

## Key Points:
- Internal data is hidden from outside.
- Only methods can access/modify data.
- Prevents unauthorized access.
- Ensures data integrity and security.
- Achieved through private fields and public methods.

## Question: What is abstraction in software design?

## Answer:
Abstraction in software design is the process of hiding complex implementation details while exposing only the essential features of an object or system. It allows developers to work with a simplified view of complex systems, focusing on what something does rather than how it does it.

I use abstraction to reduce cognitive load. When I design a payment system, I don't want every part of the system to know about credit card processing details. I create a PaymentProcessor interface that exposes a simple `processPayment` method, and the complex implementation is hidden.

Abstraction is achieved through interfaces, abstract classes, and API design. It's a fundamental principle that makes systems easier to understand, use, and modify.

## Key Points:
- Hides complexity, exposes simplicity.
- Focuses on what, not how.
- Achieved through interfaces and abstract classes.
- Reduces cognitive load.
- Makes systems easier to understand and modify.

## Question: How do interfaces help abstraction?

## Answer:
Interfaces define a contract of methods that a class must implement, without specifying how those methods are implemented. This allows you to program to an interface rather than a concrete implementation, which is the essence of abstraction.

When I use an interface, I can swap implementations without changing the code that uses them. For example, a `PaymentProcessor` interface can have `CreditCardProcessor`, `PayPalProcessor`, and `StripeProcessor` implementations.

```java
public interface PaymentProcessor {

public class CreditCardProcessor implements PaymentProcessor {

    }
}

public class PayPalProcessor implements PaymentProcessor {
    public PaymentResult processPayment(double amount) {
        // PayPal logic
    }
}
```

The consumer code only knows about `PaymentProcessor`, not the specific implementation. This makes the code flexible, testable, and easy to extend.

## Key Points:
- Define contracts without implementation details.
- Enable programming to interfaces.
- Allow swapping implementations easily.
- Make code flexible and testable.
- Foundation of dependency inversion.

## Question: What are abstract classes?

## Answer:
An abstract class is a class that cannot be instantiated directly. It can contain both abstract methods (without implementation) and concrete methods (with implementation). Subclasses must implement all abstract methods to be concrete.

I use abstract classes when I want to provide a common base with shared implementation, while forcing subclasses to provide specific implementations for certain methods. It's a middle ground between a concrete class and an interface.

```java
public abstract class Shape {
    protected String color;
    
    public Shape(String color) {
        this.color = color;
    }
    
    public abstract double area();  // no implementation
    
    public void display() {  // concrete method
        System.out.println("Color: " + color);
    }
}

public class Circle extends Shape {
    private double radius;
    
    public Circle(String color, double radius) {
        super(color);
        this.radius = radius;
    }
    
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

Abstract classes provide a template for subclasses while allowing customization. They're useful when you need to share code among related classes.

## Key Points:
- Cannot be instantiated.
- Can have both abstract and concrete methods.
- Subclasses must implement abstract methods.
- Provides shared implementation for subclasses.
- Use when classes share common behavior.

Explain the difference between abstract classes and interfaces. Abstract classes can have state and implementation; interfaces cannot (traditionally).

## Inheritance & Polymorphism

## Question: What is inheritance?

## Answer:
Inheritance is a mechanism in OOP where a new class acquires the properties and behaviors of an existing class. The new class (subclass/child) extends the existing class (superclass/parent) and inherits its fields and methods.

Inheritance establishes an "is-a" relationship. A Dog is an Animal, so Dog can inherit from Animal. This promotes code reuse â€” common functionality is defined once in the parent class and inherited by all children.

```java
public class Vehicle {
    protected int speed;
    
    public void start() {
        System.out.println("Vehicle started");
    }
}

public class Car extends Vehicle {
    private int doors;
    
    public void honk() {
        System.out.println("Beep!");
    }
}

Car myCar = new Car();
myCar.start();  // inherited from Vehicle
myCar.honk();   // defined in Car
```

Inheritance is powerful but should be used judiciously. Overuse can lead to deep hierarchies that are hard to understand and maintain.

## Key Points:
- New class acquires properties of existing class.
- Establishes "is-a" relationship.
- Promotes code reuse.
- Child can override parent methods.
- Use judiciously to avoid deep hierarchies.

## Interview Tip:
Explain the "is-a" relationship clearly. Warn about the diamond problem in multiple inheritance and how Java handles it with interfaces.

## Question: Why do we use inheritance?

## Answer:
We use inheritance primarily for code reuse and to establish natural hierarchies between related classes. When multiple classes share common behavior, inheritance lets us define that behavior once in a parent class rather than duplicating it in every child class.

Inheritance also enables polymorphism. By coding to a parent type, you can work with any child type interchangeably. This makes code more flexible and extensible.

```java
public abstract class Animal {
    public abstract void sound();
    
    public void sleep() {
        System.out.println("Sleeping...");
    }
}

public class Dog extends Animal {
    public void sound() {
        System.out.println("Bark");
    }
}

public class Cat extends Animal {
    public void sound() {
        System.out.println("Meow");
    }
}

// Polymorphism enabled by inheritance
Animal myPet = new Dog();
myPet.sound();  // Bark
```

Inheritance is useful when there's a genuine hierarchical relationship, but composition is often a better alternative for code reuse.

## Key Points:
- Promotes code reuse.
- Establishes natural hierarchies.
- Enables polymorphism.
- Reduces code duplication.
- Prefer composition when there's no clear hierarchy.

## Interview Tip:
Explain that inheritance is about "is-a" relationships and polymorphism, while composition is about "has-a" relationships and flexibility.

## Question: What are the types of inheritance?

## Answer:
There are several types of inheritance: single, multilevel, hierarchical, and multiple (through interfaces). Java supports all except multiple inheritance with classes (to avoid the diamond problem).

Single inheritance: one parent, one child. Multilevel: a chain of inheritance (A â†’ B â†’ C). Hierarchical: one parent, many children. Multiple: a child inherits from multiple parents (only with interfaces in Java).

```java
// Single inheritance
class Animal { }
class Dog extends Animal { }

// Multilevel inheritance
class Animal { }
class Dog extends Animal { }
class Puppy extends Dog { }

// Hierarchical inheritance
class Animal { }
class Dog extends Animal { }
class Cat extends Animal { }
```

Multiple inheritance with classes is not supported in Java because of the diamond problem â€” when two parent classes have the same method, the compiler doesn't know which one to call. Java solves this by allowing multiple interface inheritance.

## Key Points:
- Single: one parent, one child.
- Multilevel: chain of inheritance.
- Hierarchical: one parent, many children.
- Multiple: only through interfaces in Java.
- Java avoids diamond problem with single class inheritance.

## Interview Tip:
Explain the diamond problem clearly and why Java chose to avoid it. This shows understanding of language design decisions.

## Question: What are the disadvantages of inheritance?

## Answer:
Inheritance has several disadvantages. It creates tight coupling between parent and child classes â€” changes in the parent can break children. It makes code harder to understand because behavior can come from multiple levels in the hierarchy. It also makes testing more difficult because you can't easily mock a parent class.

Deep inheritance hierarchies are particularly problematic. When behavior is spread across many levels, it becomes hard to trace where a method is defined. This is called the "fragile base class" problem.

```java
// Fragile base class problem
class ArrayList {
    public void add(Object item) {
        // implementation
    }
}

class CountingList extends ArrayList {
    private int count = 0;
    
    public void add(Object item) {
        count++;
        super.add(item);
    }
    
    public int getCount() {
        return count;
    }
}

// Bug: addAll calls add internally
// so count is incremented for each item
// even though we didn't call add directly
```

Composition is often preferred because it avoids these issues while providing the same benefits of code reuse.

## Key Points:
- Creates tight coupling between parent and child.
- Fragile base class problem.
- Deep hierarchies are hard to understand.
- Makes testing and mocking difficult.
- Composition is often preferred.

## Question: What is method overriding?

## Answer:
Method overriding occurs when a subclass provides a specific implementation of a method that is already defined in its parent class. The overridden method must have the same name, return type, and parameters. The subclass version is called instead of the parent version at runtime.

Overriding is the mechanism behind runtime polymorphism. It allows subclasses to customize behavior while maintaining the parent's interface.

```java
public class Animal {
    public void sound() {
        System.out.println("Some generic sound");
    }
}

public class Dog extends Animal {
    @Override
    public void sound() {
        System.out.println("Bark");
    }
}

Animal myAnimal = new Dog();
myAnimal.sound();  // Output: Bark (not "Some generic sound")
```

The `@Override` annotation is optional but recommended â€” it tells the compiler to verify that you're actually overriding a parent method. This catches typos and signature mismatches at compile time.

## Key Points:
- Subclass redefines a parent method.
- Same name, return type, and parameters.
- Enables runtime polymorphism.
- `@Override` annotation is recommended.
- Called based on actual object type, not reference type.

## Interview Tip:
Explain dynamic dispatch â€” the JVM determines which method to call at runtime based on the actual object type, not the reference type.

## Question: What is method overloading?

## Answer:
Method overloading occurs when a class has multiple methods with the same name but different parameter lists (different number, types, or order of parameters). The compiler determines which method to call based on the arguments passed. This is compile-time polymorphism.

Overloading is useful when you want the same operation to work with different input types or combinations.

```java
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
    
    public double add(double a, double b) {
        return a + b;
    }
    
    public int add(int a, int b, int c) {
        return a + b + c;
    }
}
```

Overloading is resolved at compile time based on the method signature. It's different from overriding, which is resolved at runtime based on the actual object type. Overloading improves readability by providing intuitive method names.

## Key Points:
- Same method name, different parameter lists.
- Resolved at compile time (static polymorphism).
- Different from overriding (runtime polymorphism).
- Improves code readability.
- Parameters must differ in number, type, or order.

## Interview Tip:
Clarify the difference between overloading and overriding. Overloading = compile-time, same class. Overriding = runtime, parent-child relationship.

## Question: What is runtime polymorphism?

## Answer:
Runtime polymorphism (dynamic polymorphism) occurs when a method call is resolved at runtime based on the actual type of the object, not the reference type. This is achieved through method overriding â€” a subclass provides its own implementation of a parent method.

When you call an overridden method through a parent reference, the JVM determines which version to execute based on the actual object type. This is called dynamic dispatch.

```java
public class Shape {
    public double area() {
        return 0;
    }
}

public class Circle extends Shape {
    private double radius;
    
    public double area() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle extends Shape {
    private double width, height;
    
    public double area() {
        return width * height;
    }
}

Shape s1 = new Circle(5);
Shape s2 = new Rectangle(4, 6);

System.out.println(s1.area());  // 78.54
System.out.println(s2.area());  // 24.0
```

Runtime polymorphism makes code flexible and extensible. You can add new shapes without changing code that works with Shape references.

## Key Points:
- Method call resolved at runtime.
- Based on actual object type, not reference type.
- Achieved through method overriding.
- Called dynamic dispatch.
- Makes code flexible and extensible.

## Interview Tip:
Explain dynamic dispatch clearly. The reference type determines what methods are available; the actual object type determines which implementation is called.

## Question: What is compile-time polymorphism?

## Answer:
Compile-time polymorphism (static polymorphism) occurs when the method to be called is determined at compile time based on the method signature. This is achieved through method overloading â€” the compiler selects the appropriate method based on the arguments passed.

Unlike runtime polymorphism, there's no dynamic dispatch involved. The compiler knows exactly which method to call, making it slightly more efficient.

```java
public class Printer {
    public void print(String text) {
        System.out.println("Printing string: " + text);
    }
    
    public void print(int number) {
        System.out.println("Printing number: " + number);
    }
    
    public void print(String text, int copies) {
        for (int i = 0; i < copies; i++) {
            System.out.println("Printing: " + text);
        }
    }
}

Printer printer = new Printer();
printer.print("Hello");      // calls print(String)
printer.print(42);           // calls print(int)
printer.print("Hello", 3);   // calls print(String, int)
```

Compile-time polymorphism is resolved by the compiler through a process called static binding or early binding.

## Key Points:
- Resolved at compile time.
- Achieved through method overloading.
- No dynamic dispatch involved.
- More efficient than runtime polymorphism.
- Also called static polymorphism.

## Interview Tip:
Explain that Java also uses compile-time polymorphism for resolving overloaded methods. The compiler looks at argument types to determine the correct method.

## Question: Why is composition often preferred over inheritance?

## Answer:
Composition is often preferred over inheritance because it provides more flexibility, loose coupling, and avoids the fragile base class problem. With composition, you can change behavior at runtime by swapping contained objects, whereas inheritance is fixed at compile time.

Composition also avoids deep inheritance hierarchies. Instead of a complex tree of classes, you build behavior by combining small, focused objects. This makes code easier to understand, test, and maintain.

```java
// Composition approach

    void start();
}

public class GasEngine implements Engine {
    public void start() {
        System.out.println("Gas engine started");
    }
}

public class ElectricEngine implements Engine {
    public void start() {
        System.out.println("Electric engine started");
    }
}

public class Car {
    private Engine engine;  // can swap at runtime
    
    public Car(Engine engine) {
        this.engine = engine;
    }
    
    public void start() {
        engine.start();
    }
}
```

With composition, you can create different car types by passing different engines, without needing separate Car subclasses for each engine type.

## Key Points:
- More flexible than inheritance.
- Loose coupling between components.
- Can change behavior at runtime.
- Avoids fragile base class problem.
- Preferred unless there's a clear "is-a" relationship.

Give a clear example showing how composition is more flexible. Emphasize that "has-a" relationships are more common than "is-a" relationships.

## Answer:
You should use inheritance when there's a genuine "is-a" relationship between classes and you want to share common implementation. For example, a Dog is an Animal, so Dog inheriting from Animal makes sense. The parent provides shared behavior, and the child specializes it.

Inheritance is also appropriate when you want polymorphism â€” treating different child types through a common parent reference. This is useful in frameworks and plugin systems.

- There's a clear hierarchical relationship.
- You need polymorphism.

## SOLID Principles

## Question: What are SOLID principles?

## Answer:
SOLID is an acronym for five design principles that make object-oriented code more maintainable, flexible, and robust. They were introduced by Robert C. Martin (Uncle Bob) and are fundamental to good software design.

The five principles are:
- **S**ingle Responsibility Principle (SRP): A class should have only one reason to change.
- **O**pen/Closed Principle (OCP): Software entities should be open for extension but closed for modification.
- **L**iskov Substitution Principle (LSP): Subtypes must be substitutable for their base types.
- **I**nterface Segregation Principle (ISP): Clients should not depend on interfaces they don't use.
- **D**ependency Inversion Principle (DIP): High-level modules should not depend on low-level modules; both should depend on abstractions.

I apply these principles in every project I work on. They help me write code that's easier to test, modify, and extend.

## Key Points:
- SRP: one reason to change.
- OCP: open for extension, closed for modification.
- LSP: subtypes must be substitutable.
- ISP: don't depend on unused interfaces.
- DIP: depend on abstractions, not concretions.

## Interview Tip:
Know each principle by name and be able to explain it with a code example. Interviewers often ask about specific principles.

---

## Question: What is the Single Responsibility Principle (SRP)?

## Answer:
The Single Responsibility Principle states that a class should have only one reason to change. In other words, a class should have only one job or responsibility. This makes the class easier to understand, test, and maintain.

I follow SRP by ensuring each class does one thing well. If a class is handling both user management and email sending, I split it into two classes. This way, changes to email functionality don't risk breaking user management.

```java
// Violates SRP
```

## Question: What is the Liskov Substitution Principle (LSP)?

## Answer:
The Liskov Substitution Principle states that objects of a subclass should be able to replace objects of the parent class without affecting the correctness of the program. In other words, if S is a subtype of T, then objects of type T should be replaceable with objects of type S without breaking anything.

LSP ensures that inheritance is used correctly. A subclass should honor the contract of its parent class. If a subclass changes the behavior of a parent method in a way that surprises the caller, it violates LSP.

```java
// Violates LSP
class Rectangle {
    protected int width, height;
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}

class Square extends Rectangle {
    public void setWidth(int w) {
        width = w;
        height = w;  // changes height too!
    }
}

// Client expects rectangle behavior
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(3);
// r.area() returns 15, but Square's behavior is different
```

LSP is about behavioral compatibility â€” subclasses must not change the expected behavior of parent methods.

## Key Points:
- Subtypes must be substitutable for base types.
- Subclasses must honor parent class contracts.
- Behavioral compatibility is required.
- Violations lead to unexpected bugs.
- Ensure subclasses don't change expected behavior.

## Question: What is the Dependency Inversion Principle (DIP)?

## Answer:
The Dependency Inversion Principle states that high-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

I follow DIP by depending on interfaces rather than concrete implementations. This makes the system flexible and easier to test because I can swap implementations without changing the high-level code.

```java
}

// Follows DIP

    void save(Order order);
}

class OrderService {
    private Database database;
    
    public OrderService(Database database) {
        this.database = database;
    }
    
    public void saveOrder(Order order) {
        database.save(order);
    }
}
```

With DIP, I can easily switch from MySQL to PostgreSQL by creating a new Database implementation. The OrderService doesn't change.

## Key Points:
- High-level modules depend on abstractions, not details.
- Both modules depend on abstractions.
- Abstractions don't depend on details.
- Makes code flexible and testable.
- Enables dependency injection.

## Question: How do you implement Singleton?

## Answer:
There are several ways to implement Singleton. The simplest is lazy initialization with double-checked locking for thread safety. In Java, you can use an enum or a static holder class for a cleaner implementation.

```java
// Double-checked locking
public class Singleton {
    private static volatile Singleton instance;
    
    private Singleton() {}
    
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

// Bill Pugh approach (preferred)
public class Singleton {
    private Singleton() {}
    
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    
    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

The Bill Pugh approach is preferred because it's thread-safe without synchronization overhead and leverages the class loader's lazy initialization.

- Private constructor prevents instantiation.
- Static instance field holds the single instance.
- Double-checked locking for thread safety.
- Bill Pugh approach is preferred.

## Builder Pattern

## Question: What is Builder Pattern?

## Answer:
Builder pattern is a creational design pattern that separates the construction of a complex object from its representation. It allows you to construct different types and representations of an object using the same construction code. The Builder pattern is especially useful when an object has many optional parameters.

I use Builder when constructing objects with many parameters, especially when some are optional. Instead of creating multiple constructor overloads, I use a fluent API that makes the code readable and maintainable.

```java

        public Builder age(int age) {
            user.age = age;
            return this;
        }
        
        public Builder phone(String phone) {
            user.phone = phone;
            return this;
        }
        
        public User build() {
            return user;
        }
    }
}
```

## Strategy Pattern

## Question: What is Strategy Pattern?

## Answer:
Strategy pattern is a behavioral design pattern that defines a family of algorithms, encapsulates each one, and makes them interchangeable. It lets the algorithm vary independently from clients that use it. I use it to eliminate complex conditional logic and make code more flexible.

The key idea is to extract each algorithm into its own class that implements a common interface. The context class holds a reference to the current strategy and delegates the work to it. This allows you to change the algorithm at runtime without modifying the context.

```java
public interface SortStrategy {
    void sort(int[] array);
}

public class BubbleSort implements SortStrategy {
    public void sort(int[] array) {
        // Bubble sort implementation
    }
}

public class QuickSort implements SortStrategy {
    public void sort(int[] array) {
        // Quick sort implementation
    }
}

public class Sorter {
    private SortStrategy strategy;
    
    public Sorter(SortStrategy strategy) {
        this.strategy = strategy;
    }
    
    public void sort(int[] array) {
        strategy.sort(array);
    }
    
    public void setStrategy(SortStrategy strategy) {
        this.strategy = strategy;
    }
}
```

## Key Points:
- Defines a family of algorithms.
- Encapsulates each algorithm in its own class.
- Algorithms are interchangeable at runtime.
- Eliminates complex conditional logic.
- Follows Open/Closed Principle.

## Observer Pattern

## Question: What is the Observer design pattern?

## Answer:
Observer pattern is a behavioral design pattern that defines a one-to-many dependency between objects. When one object (the subject) changes state, all its dependents (observers) are notified and updated automatically. This is the foundation of event-driven programming.

I use Observer when I need to notify multiple objects about changes without tightly coupling them. The subject doesn't need to know what the observers do with the information â€” it just notifies them.

```typescript
interface Observer {
    update(data: any): void;
}

class Subject {
    private observers: Observer[] = [];
    
    subscribe(observer: Observer) {
        this.observers.push(observer);
    }
    
    unsubscribe(observer: Observer) {
        this.observers = this.observers.filter(o => o !== observer);
    }
    
    notify(data: any) {
        this.observers.forEach(observer => observer.update(data));
    }
}

class EmailNotification implements Observer {
    update(data: any) {
        console.log(`Email: ${data.message}`);
    }
}

class SMSNotification implements Observer {
    update(data: any) {
        console.log(`SMS: ${data.message}`);
    }
}
```

## Key Points:
- One-to-many dependency between objects.
- Subject notifies observers automatically.
- Observers are loosely coupled to subject.
- Foundation of event-driven programming.
- Follows Open/Closed Principle.

## Question: What is Proxy Pattern?

## Answer:
Proxy pattern is a structural design pattern that provides a surrogate or placeholder for another object to control access to it. The proxy has the same interface as the real object and controls how the client interacts with it.

I use Proxy for lazy loading, access control, caching, and logging. The proxy intercepts requests and can add behavior before or after delegating to the real object.

```typescript
interface Image {
    display(): void;
}

class RealImage implements Image {
    private filename: string;
    
    constructor(filename: string) {
        this.filename = filename;
        this.loadFromDisk();
    }
    
    private loadFromDisk() {
        console.log(`Loading ${this.filename} from disk`);
    }
    
    display() {
        console.log(`Displaying ${this.filename}`);
    }
}

class ProxyImage implements Image {
    private realImage: RealImage | null = null;
    private filename: string;
    
    constructor(filename: string) {
        this.filename = filename;
    }
    
    display() {
        if (!this.realImage) {
            this.realImage = new RealImage(this.filename);
        }
        this.realImage.display();
    }
}

// Usage
const image: Image = new ProxyImage("photo.jpg");
// Image not loaded yet
image.display(); // Loads and displays
image.display(); // Just displays (already loaded)
```

## Key Points:
- Provides placeholder for another object.
- Controls access to the real object.
- Same interface as real object.
- Useful for lazy loading, caching, access control.
- Adds behavior without modifying real object.

## Question: How would you design product inventory management?

## Answer:
I'd design product inventory management with Product, Inventory, and Stock entities. The inventory tracks stock levels and handles reservations.

```java
public class Inventory {
    private Map<String, Integer> stockLevels;
    private Map<String, Integer> reservedStock;
    
    public boolean isAvailable(String productId, int quantity) {
        int available = getAvailableStock(productId);
        return available >= quantity;
    }
    
    public int getAvailableStock(String productId) {
        int total = stockLevels.getOrDefault(productId, 0);
        int reserved = reservedStock.getOrDefault(productId, 0);
        return total - reserved;
    }

            throw new InsufficientStockException();

        reservedStock.merge(productId, -quantity, Integer::sum);
    }
    
    public void deduct(String productId, int quantity) {
        stockLevels.merge(productId, -quantity, Integer::sum);
        reservedStock.merge(productId, -quantity, Integer::sum);
    }
}
```
